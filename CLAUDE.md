# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

InvoiceBuilder is a .NET 9 **Blazor Web App** using the **Interactive Server** render mode (Blazor Server over SignalR — no WebAssembly). It manages senders, customers, and invoices, and renders invoices to PDF. The domain is fully modeled: `Sender`, `Customer`, `Invoice`, and `InvoiceLineItem` in [Models/](Models/), with CRUD pages under [Components/Pages/](Components/Pages/).

## Commands

```powershell
# Restore npm deps once (required — the build shells out to the Tailwind CLI)
npm install

dotnet run                      # build + run (http://localhost:5036, https://localhost:7032)
dotnet watch                    # run with hot reload
dotnet build                    # build only

# EF Core migrations (tools are referenced in the csproj)
dotnet ef migrations add <Name>
dotnet ef database update       # usually unnecessary — see "migrations on startup" below
```

There is no test project or test runner (`package.json`'s `test` script is a placeholder stub).

## Architecture notes

- **Database is SQLite, not SQL Server.** Despite the `DefaultConnection`/LocalDB heritage, the app runs on SQLite (`invoicebuilder.db` in the project root). [Program.cs](Program.cs) calls `UseSqlite`, and [Data/DesignTimeDbContextFactory.cs](Data/DesignTimeDbContextFactory.cs) hardcodes the SQLite connection so `dotnet ef` works at design time. Both the `Sqlite` and `SqlServer` EF providers are referenced in the csproj; to switch providers, change `UseSqlite` in `Program.cs` **and** the factory, and regenerate migrations.

- **Migrations and seed data apply on startup.** [Program.cs](Program.cs) calls `db.Database.Migrate()` at boot and seeds one sample sender/customer/invoice if `Senders` is empty. You rarely need `dotnet ef database update` — just run the app. Deleting `invoicebuilder.db*` resets everything.

- **Data access uses a DbContext *factory*, not a scoped context.** Services (`SenderService`, `CustomerService`, `InvoiceService` in [Services/](Services/)) are registered `Scoped` but take `IDbContextFactory<ApplicationDbContext>` and create a short-lived `db` per method (`await using var db = factory.CreateDbContext()`). This is the Blazor Server pattern — a long-lived scoped context would leak state across a circuit's concurrent renders. Reads use `.AsNoTracking()`. Follow this pattern for any new service.

- **Disconnected line-item reconciliation.** `InvoiceService.UpdateAsync` deliberately loads the tracked `Invoice` graph and diffs `LineItems` (add/update/remove) rather than calling `db.Update()`, because a blanket update won't delete rows the user removed in the editor. Preserve this diff logic when touching invoice editing.

- **PDF generation via QuestPDF.** [Services/InvoiceDocument.cs](Services/InvoiceDocument.cs) is an `IDocument` that lays out the invoice with the QuestPDF Fluent API. The Community license is set at the top of [Program.cs](Program.cs) (required, or QuestPDF throws at runtime). A minimal-API endpoint `GET /invoices/{id}/pdf` (bottom of `Program.cs`) streams the generated bytes — this is the one non-component HTTP route.

- **Computed money fields are `[NotMapped]`.** `Invoice.Subtotal/TaxAmount/Total` and `InvoiceLineItem.LineTotal` are derived properties, not columns. Decimal precision for the mapped columns (`TaxRate`, `Quantity`, `UnitPrice`) is configured in `ApplicationDbContext.OnModelCreating`, which also sets the unique index on `InvoiceNumber` and the cascade/restrict delete behaviors.

- **Tailwind is wired into the .NET build.** The `Tailwind` MSBuild target in [InvoiceBuilder.csproj](InvoiceBuilder.csproj) runs `npx @tailwindcss/cli -i app.css -o wwwroot/app.css` on every build (Tailwind v4). Edit the source [app.css](app.css), never the generated `wwwroot/app.css`. `npm install` and Node/npx must be available or the build fails.

- **Three CSS systems coexist.** Pages lean primarily on **Tailwind utility classes** plus a set of custom component classes defined in `app.css` (`card`, `btn-primary`, `btn-secondary`, `page-title`, `page-subtitle`). **MudBlazor** (v9.6) is also available and its providers are wired up; **Bootstrap** ships from the default template. Be deliberate about which one you reach for — new pages here use Tailwind + the custom classes.

- **MudBlazor** services are registered via `AddMudServices()` in `Program.cs`, the providers (`MudThemeProvider`, `MudPopoverProvider`, `MudDialogProvider`, `MudSnackbarProvider`) live in [Components/Layout/MainLayout.razor](Components/Layout/MainLayout.razor), and `@using MudBlazor` is global via [Components/_Imports.razor](Components/_Imports.razor). `ISnackbar` is the toast mechanism used by the edit pages.

- **Forms use Blazor `EditForm` + DataAnnotations.** Validation attributes live on the model classes (`[Required]`, `[Range]`, `[StringLength]`); edit pages wrap a `<DataAnnotationsValidator />` in an `EditForm` and submit via `OnValidSubmit`. `Program.cs` is the single composition root — register services and middleware there.

- **AI invoice drafting calls Gemini, never saves directly.** [Modules/AiInvoiceDrafting/](Modules/AiInvoiceDrafting/) (`/ai-invoice-draft`) sends a plain-English request to `GeminiInvoiceDraftService`, which uses Gemini's `responseSchema`/`responseMimeType: application/json` structured output (not regex-parsed prose) and includes the existing customer-name list in the prompt so the model can resolve name variants to a real customer. The parsed draft is read-only preview until the user clicks through to `/invoices/new`; the handoff goes through `Services/DraftInvoiceHandoff.cs` (a scoped, same-circuit in-memory service), not a direct cross-slice service call — `AiInvoiceDrafting` and `Invoices` never reference each other, per the vertical-slice rules. The API key lives in `Ai:Gemini:ApiKey` config (user-secrets/env var, never `appsettings.json`) — see [.claude/rules/modules.md](.claude/rules/modules.md).
